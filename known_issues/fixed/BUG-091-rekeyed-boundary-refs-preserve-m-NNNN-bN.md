# BUG-091: rekeyed boundary refs must preserve m-NNNN refs that syntactically match bN

**Status:** Fixed 2026-08-10
**Severity:** Low
**Component:** lib/state/inherit.ts::rekeyBlocksToFork (inline boundary-ID guard)

## Resolution (2026-08-10)

When re-keying inherited compression blocks to the fork's `timeToId`, raw message-ID
boundary refs like `m0042` that _syntactically_ look like block IDs (`bN`) were being
misclassified by the block-ID lookup and re-keyed (sometimes to empty strings),
corrupting `startId`/`endId` of the inherited block.

**Fix:** inline `parseBoundaryId(b.startId) ? b.startId : (timeToId.get(b.startTime) ?? "")`
guard in `rekeyBlocksToFork` at `lib/state/inherit.ts:199-200`. The guard routes any value
that `parseBoundaryId` recognizes as a recognized boundary ref (`mNNNN` or `bN`) through
the rekey path; raw `m-NNNN` (and other unrecognized formats) pass through verbatim.

`parseBoundaryId` is imported from `../message-ids` at `lib/state/inherit.ts:24` and
returns a `ParsedBoundaryId` (`kind: 'message'` for `mNNNN` or `kind: 'compressed-block'` for `bN`) — `null` for everything else. The
fix is a 2-line inline guard; the helper already existed and was simply not being
consulted by the rekey path.

**Test:** `tests/session-fork-inherit.test.ts:609` `BUG-091: rekey-blocks-to-fork-preserves-boundary-refs`
test case (boundary ID with raw `m-NNNN` syntax preserved verbatim through rekey).

**Severity rationale:** Latent correctness guard, no user-reported impact at time of
fix. Architect-verified Low (small-architect verdict): the bug is in a code path that
existed prior to BUG-089's protocol-layer work and was exposed by it; without an
inheritance feature in the hot path, the field would never be re-keyed. Same cluster
shape as BUG-089's "Architect-Verified Severity Adjustments" — latent-defect, not a
runtime incident.

## Problem

Compression blocks reference messages via `startId` / `endId`. After a fork, those
message IDs are regenerated by OpenCode, so `rekeyBlocksToFork` rebuilds the
references via the fork's `timeToId` index. The defect: when a `startId` is a raw
message ref like `"m0042"` and the rekey code matched on the `bN` syntactic pattern
alone, the message ref was treated as a block ID and either silently re-keyed to an
unrelated block ID or to an empty string — both corrupt the block graph.

## Root cause

`rekeyBlocksToFork` (`lib/state/inherit.ts:194-219`) maps inherited blocks to the
fork's message-ID namespace. The block's `startId` / `endId` are boundary refs
(`mNNNN` or `bN`), not message IDs — they live in a session-relative namespace that
forks inherit verbatim (ref assignment is deterministic over identical message lists,
so the same message gets the same ref in B). The original code re-keyed everything via
`timeToId.get(b.startTime)`, which only works for raw message IDs in B's namespace.
When the value was a raw `m0042` ref, the lookup either matched an unrelated entry,
returned `undefined` and coerced to `""`, or matched an unrelated block ID.

The fix is a 2-line inline guard at `lib/state/inherit.ts:199-200`: consult
`parseBoundaryId` first and pass any recognized boundary ref (`mNNNN` or `bN`) through
verbatim; only fall back to the `timeToId` lookup when the value is unrecognized. The helper
already existed (imported at `lib/state/inherit.ts:24` from `lib/message-ids.ts`) and
was simply not being consulted by the rekey path — no refactor required.
